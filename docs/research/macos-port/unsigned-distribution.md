# Unsigned Public Distribution on macOS

**Scope.** Research for [Nightchamp/arknights-frame-assistant#9](https://github.com/Nightchamp/arknights-frame-assistant/issues/9), “调研未签名公开分发的安装、权限与更新约束”. The selected product boundary is an open-source, public GitHub-style release for Apple silicon, without Developer ID signing or notarization, whose users accept a manual Gatekeeper override. This report treats the selected “unsigned” artifact as ad-hoc signed; a private-CA or self-signed certificate would be a different distribution design. Public sources were checked on 2026-08-08 through `agent-reach`, using primary Apple sources and Sparkle's first-party documentation.

## Executive Finding

The selected release is feasible only as a deliberately high-friction, user-level product. The app can be distributed publicly, manually exempted from Gatekeeper, and granted standard TCC permissions by the user. It cannot offer a verified publisher, notarization, dependable TCC permission continuity across changed builds, restricted entitlements, or the current supported app-bundled privileged LaunchDaemon path through `SMAppService`. Legacy or manually installed root-daemon paths are technically distinct, but they are deprecated or operationally separate, update-hostile, and not justified by the current requirements. An updater can authenticate its own archives with Sparkle EdDSA, but it cannot repair the missing operating-system identity: an updated ad-hoc-signed build can still lose Accessibility, Input Monitoring, Screen Recording, Automation, or other identity-bound authorization.

For Apple silicon, “unsigned” should mean **not signed by an Apple-issued identity**, not literally lacking a code signature. Apple silicon requires executable code to be at least ad-hoc signed; Xcode calls this **Sign to Run Locally**. An ad-hoc signature has no cryptographic signer identity and identifies only that particular code, so it does not provide release-to-release identity or publisher authenticity ([Apple DTS: C++ default project and ad-hoc signing](https://developer.apple.com/forums/thread/703059); [Apple Code Signing Requirement Language](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/RequirementLang/RequirementLang.html)).

## Facts

### 1. Quarantine, Gatekeeper, and the manual installation path

- A GitHub ZIP downloaded with Safari is quarantined. Apple documents Safari's use of the `com.apple.quarantine` extended attribute and states that launching a quarantined app always invokes Gatekeeper; Gatekeeper may also run in other circumstances that Apple does not document as a stable policy ([Resolving Trusted Execution Problems](https://developer.apple.com/forums/thread/706442)).
- Gatekeeper normally checks that downloaded software comes from an identified developer, is notarized, has not been altered, and is intentionally being opened. An ad-hoc release satisfies neither identified-developer nor notarization policy, so ordinary first launch is expected to be blocked ([Gatekeeper and runtime protection](https://support.apple.com/guide/security/gatekeeper-and-runtime-protection-sec5599b66df/web)).
- Apple's current documented override is: try to open the app once; open **System Settings > Privacy & Security**; in **Security**, choose **Open Anyway** while the option is available; authenticate; then confirm **Open**. Apple says the option is available for about an hour after the failed launch and that the approved app is saved as an exception for future ordinary launches ([Open an app from an unknown developer](https://support.apple.com/guide/mac-help/open-a-mac-app-from-an-unknown-developer-mh40616/mac)).
- The supported product instructions should not tell users to disable Gatekeeper globally or strip quarantine with `xattr`. Those actions remove provenance rather than recording the narrow user decision that Apple's override UI is designed to capture.
- Gatekeeper may execute a downloaded app from a randomized, read-only translocation path. Apple does not document the exact triggering rules and advises apps to work correctly whether translocated or not ([Gatekeeper and runtime protection](https://support.apple.com/guide/security/gatekeeper-and-runtime-protection-sec5599b66df/web); [App Translocation Notes](https://developer.apple.com/forums/thread/724969)). The release instructions should therefore make the user move the app into `/Applications` before first launch, permission requests, login-item registration, or update setup.
- Manual approval does not turn the app into identified-developer software. macOS still cannot present a verified publisher or use a Developer ID/notarization ticket to prove that the download is the developer's unmodified release. A GitHub checksum or updater signature can add project-level verification, but it is not a Gatekeeper identity.

### 2. TCC identity and permission persistence

TCC controls the permissions most likely to matter to the macOS implementation, including Accessibility, Input Monitoring, Screen Recording, Automation, and access to protected files. These are user decisions enforced independently of ordinary Unix ownership and root privileges ([Protecting app access to user data](https://support.apple.com/guide/security/protecting-app-access-to-user-data-secc01781f46/web); [Controlling app access to files](https://support.apple.com/guide/security/controlling-app-access-to-files-secddd1d86a6/web)). A privileged helper or `sudo` does not bypass them ([Apple DTS: Advice needed](https://developer.apple.com/forums/thread/732879)).

TCC uses code identity, with the designated requirement as a key mechanism, to decide whether a changed executable is still the app the user authorized. A normal Developer ID designated requirement can remain stable while executable bytes change. An ad-hoc signature has no certificate identity and identifies exactly one signed program; a nontrivial code change changes its Code Directory and therefore its identity ([Code Signing Requirement Language](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/RequirementLang/RequirementLang.html); [TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)). Apple DTS consequently advises that TCC permissions are not reliable across unsigned or ad-hoc builds, even when the bundle identifier is unchanged ([repeated consent](https://developer.apple.com/forums/thread/124351); [TCC with ad-hoc builds](https://developer.apple.com/forums/thread/730043)).

| Change | Expected identity result | Product contract |
|---|---|---|
| Relaunch the exact installed build without modifying it | The same ad-hoc code identity remains available, so TCC can remember a grant for that exact code. | It is reasonable to depend on permission persistence within one unchanged installation, subject to per-service testing. |
| Move or copy the exact unchanged app | The signature itself does not change merely because the file path changes, but Apple publishes no universal TCC guarantee for path changes. Unbundled helpers can be recorded by path, and translocation adds another temporary execution path ([Apple DTS helper example](https://developer.apple.com/forums/thread/692758)). | Require installation in `/Applications` before asking for permissions. Do not promise that grants survive later relocation or duplicate copies. |
| Replace the app at the same path with a changed ad-hoc build | The new code no longer has the prior build's stable designated identity. Keeping the bundle ID and path is insufficient. | Expect reauthorization, stale privacy-list entries, or prompt churn after every changed release. Detect authorization again after update and guide the user through recovery. |
| Install the same changed build manually or through Sparkle | The installation mechanism does not create an Apple signing identity. | Gatekeeper handling may differ by delivery path, but TCC continuity remains unreliable either way. |
| Split protected work into a helper | TCC's “responsible code” and bundle placement affect which process/app receives the grant; some helper cases are path-keyed. | Avoid a helper for TCC-protected work in the first release. If one becomes necessary, test each permission and process boundary independently. |

This means a first public build can ask the user for standard TCC access and work after approval, but **permission persistence across updates is not a supportable promise**. Screen capture has an explicit Apple DTS example: once an app has a stable signing identity, TCC should remember it from build to build; an unsigned or ad-hoc app lacks that property ([screen-recording permission persistence](https://developer.apple.com/forums/thread/695689)). The same identity limitation applies broadly even though individual TCC services can differ in prompting, UI, restart, and reset behavior.

### 3. Ad-hoc signing, Developer ID, hardened runtime, and notarization are distinct

| Mechanism | What it supplies | What it does not supply in this release |
|---|---|---|
| Ad-hoc code signature | A runnable Apple-silicon code object, sealed code metadata, and a place for unrestricted entitlements. | No cryptographic publisher, Team ID, stable identity across changed builds, Gatekeeper trust, or authorization for restricted entitlements. An attacker who changes the app can create a new ad-hoc signature. |
| Developer ID Application signature | An Apple-issued public distribution identity, a stable certificate/team anchor for designated requirements, and the signing basis for direct distribution and notarization. | It is deliberately excluded by the selected release boundary. |
| Hardened runtime | Runtime mitigations against injection, library hijacking, and process-memory tampering, with narrowly declared exceptions ([Hardened Runtime](https://developer.apple.com/documentation/security/hardened-runtime)). | It does not identify the publisher, satisfy Gatekeeper distribution policy, stabilize TCC identity, or produce a notarization ticket. It can technically accompany ad-hoc signing, but nested frameworks must satisfy library validation. |
| Notarization | Apple's automated malware and code-signing checks plus a ticket that Gatekeeper can retrieve or find stapled to the product. It is not App Review. | Current submissions require Developer ID signing and hardened runtime, so a current unsigned/ad-hoc release cannot be notarized ([notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution); [common issues](https://developer.apple.com/documentation/security/resolving-common-notarization-issues)). |
| Provisioning profile | Apple authorization for restricted entitlements, tied to a signing identity and App ID. | Restricted entitlements cannot be made trustworthy by writing them into an ad-hoc signature; they must be authorized by a profile ([TN3125](https://developer.apple.com/documentation/technotes/tn3125-inside-code-signing-provisioning-profiles)). |

Standard TCC permissions are not themselves a substitute for restricted entitlements, and the reverse is also true. The unsigned app may request ordinary Accessibility, Input Monitoring, or Screen Recording consent, but it cannot use Team ID/profile-dependent capabilities merely by adding entitlement keys. App Groups, shared keychain access groups, and any other selected capability documented as restricted must be treated as unavailable until the product adopts an eligible Apple signing identity and profile.

A project-generated signing certificate is not a hidden substitute for Developer ID in this report. It could create a cryptographic signature and a certificate-based designated requirement, but Gatekeeper treats non-Apple signing identities like ad-hoc signing, Apple says they buy little for public Mac distribution, and Apple does not document such an identity as a supported public TCC continuity contract ([Apple DTS: non-Apple code-signing identities](https://developer.apple.com/forums/thread/682140)). Adopting one would require a separate security and clean-system TCC prototype; it is not part of the chosen ad-hoc release.

### 4. Privileged helpers and `SMAppService`

Apple's current `SMAppService` API controls login items, LaunchAgents, and LaunchDaemons embedded in an app. Its API contract states that apps using it must be code signed, registration fails for an invalid app signature, service launch is subject to user approval, and a LaunchDaemon does not start until an administrator approves it. Most importantly for this decision, **an app that contains a LaunchDaemon must be notarized** ([`SMAppService`](https://developer.apple.com/documentation/servicemanagement/smappservice); [`register()`](https://developer.apple.com/documentation/servicemanagement/smappservice/register/); [Service Management errors](https://developer.apple.com/documentation/servicemanagement/service-management-errors)). Current notarization in turn requires Developer ID.

The older `SMJobBless` route does not remove signing from the design. It requires the calling app and helper to be signed, the app to identify owned helpers with `SMPrivilegedExecutables` code requirements, and the helper to authorize clients with reciprocal `SMAuthorizedClients` requirements. Apple deprecated it in macOS 13 in favor of `SMAppService` ([`SMJobBless`](https://developer.apple.com/documentation/servicemanagement/smjobbless(_:_:_:_:))). An ad-hoc requirement can identify one exact helper build, but it cannot provide stable public update ownership across changed builds.

These constraints apply to persistent privileged helpers, not every user-level background feature. A nonprivileged login item or LaunchAgent is a separate `SMAppService` case and may be technically testable with a properly ad-hoc-signed bundle, but its registration/update behavior is not evidence that a privileged LaunchDaemon is allowed. It also does not improve TCC identity.

### 5. Sparkle and equivalent update security

Sparkle separates update authenticity from Apple code signing. It instructs publishers to serve over HTTPS and to sign every published update archive, binary delta, and installer package with Sparkle's EdDSA/Ed25519 key. The public key is embedded as `SUPublicEDKey`, while `generate_appcast` or `sign_update` uses the private key to create the appcast signature ([Sparkle setup](https://sparkle-project.org/documentation/); [publishing](https://sparkle-project.org/documentation/publishing/)). This makes a cryptographically authenticated update channel technically possible without Developer ID.

It does not make the resulting app Developer ID signed. The unsigned release has these additional constraints:

- Sparkle recommends Developer ID signing and notarization when possible. Its distributed XPC services and helper tools are ad-hoc signed by default, which Sparkle describes as useful for common development workflows but not ideal for distribution. Alternative distribution workflows must correctly sign the nested framework and helpers ([Sparkle sandboxing and code signing](https://sparkle-project.org/documentation/sandboxing/)).
- Hardened-runtime Library Validation may refuse to load Sparkle when the host is ad-hoc signed. Sparkle documents Apple Development signing or disabling library validation for debug builds as the development remedies; Developer ID avoids the issue in distribution. Therefore “ad-hoc + hardened runtime + Sparkle” is not a combination to assume works without a release prototype ([Sparkle setup](https://sparkle-project.org/documentation/)).
- Sparkle can verify that an update came from the holder of the EdDSA private key, but the changed app still has a new ad-hoc code identity. TCC grants may stop applying immediately after an otherwise valid update.
- Sparkle's stronger `SUVerifyUpdateBeforeExtraction` option requires EdDSA, and `SURequireSignedFeed` can also authenticate the appcast and release notes. Without Developer ID, loss of the EdDSA private key removes Sparkle's documented Developer ID fallback for trusted key rotation. Existing users may then require a manual replacement to move to a new key ([Sparkle customization](https://sparkle-project.org/documentation/customization/); [Sparkle key rotation](https://sparkle-project.org/documentation/)).
- Package updates require user authorization and cannot be silent. They add no benefit for a normal app-bundle update and do not solve the notarized-LaunchDaemon requirement ([Sparkle package updates](https://sparkle-project.org/documentation/package-updates/)).

An equivalent custom updater needs the same security property: a long-lived offline-controlled signing key whose public key is pinned in the installed app, verification before extraction, and atomic replacement of the complete app bundle. A checksum published beside the archive is useful for accidental corruption but is not an authenticated update by itself if an attacker can replace both archive and checksum.

## Product Implications

| Public-release capability | Result without Developer ID | Implication for the first public version |
|---|---|---|
| Browser download and first launch | Possible after the documented manual Gatekeeper override. | Publish exact `/Applications` and **Open Anyway** steps and expect substantial trust/support friction. |
| Verified publisher, normal Gatekeeper launch, offline notarization ticket | Impossible. | macOS cannot tell users that Apple recognizes the developer or checked this release. |
| Accessibility, Input Monitoring, Screen Recording, Automation, protected-file consent | Possible for the exact installed build after user approval; continuity across changed builds is unreliable. | First-run and post-update permission diagnosis are mandatory. Do not promise a one-time permission setup. |
| Seamless background update | Archive authenticity is possible with Sparkle EdDSA; seamless continued operation is not reliable because TCC identity changes and Sparkle's ad-hoc helper/runtime combination needs validation. | Prefer release notification and manual replacement for the first version. A later in-app installer still requires an unsigned-release prototype and explicit reauthorization UX. |
| Stable keychain identity or shared access groups | Stable cross-build access is unreliable; Team ID/profile-dependent groups are unavailable. | Do not make first-version startup or recovery depend on identity-bound shared keychain state. |
| User-level launch at login | Potentially testable with an ad-hoc-signed `SMAppService.mainApp` or login item, but not established by this research. | Treat as an optional prototype, not a release assumption; recheck registration after updates. |
| App-bundled privileged helper or LaunchDaemon through current `SMAppService` | Unavailable under the combined “no Developer ID, no notarization” boundary. Legacy/manual installation is a separate, deprecated or admin-operated product path rather than an equivalent fallback. | Exclude privileged helpers from the first public version; reopen the distribution decision if one becomes essential. |
| Restricted-entitlement capabilities | Impossible without an eligible signing identity and provisioning profile. | Reject or redesign any feature whose Apple documentation requires a restricted entitlement. |
| Managed PPPC/TCC preapproval | No reliable app identity for a configuration profile to target. | Out of scope for this consumer release; users must grant access interactively. |

The core product can therefore be public and unsigned only if all first-version behavior runs in the user's session, uses APIs available with ordinary TCC consent and unrestricted entitlements, detects permission loss, and remains useful despite manual recovery after updates. Any requirement for silent maintenance, stable security identity, privileged persistence, or a restricted entitlement crosses the selected boundary.

## Boundary for the Limited Privileged-Helper Preference

Decision map #1 allows investigation of a limited privileged helper when necessary while excluding Developer ID and notarization. The current supported app-bundled installation path makes those preferences contradictory for a persistent root helper:

1. A privileged `SMAppService` LaunchDaemon must live in a properly signed app and the containing app must be notarized.
2. Current notarization requires Developer ID signing and hardened runtime.
3. The legacy `SMJobBless` alternative is deprecated and still depends on signed app/helper identities and reciprocal signing requirements that must remain meaningful across updates. A manually installed `/Library/LaunchDaemons` job is technically possible outside `SMAppService`, but it creates a separate administrator-operated installer, ownership, security, and update lifecycle rather than preserving the chosen simple app distribution.
4. Root elevation would not bypass TCC for global input, Accessibility, Screen Recording, Automation, or protected user data, so a helper cannot be used as a workaround for the product's likely privacy permissions.

“Limited” scope reduces the helper's authority but does not relax these installation and identity rules. Because current input research found no required capability that needs root, the first public version should explicitly exclude a persistent privileged helper, LaunchDaemon, privileged package updater, and helper-based attempt to bypass TCC. This is a product boundary, not a claim that macOS cannot run a manually installed daemon. If later prototype evidence proves that a required behavior truly needs root, reopen the distribution decision and compare Developer ID plus `SMAppService` against a separately administered legacy/manual component instead of silently treating either as the current release model.

## Unresolved Questions

1. Which minimum and latest macOS versions the first public version will support. Gatekeeper wording, translocation, privacy panes, and helper approval behavior change between releases.
2. For each API selected by the input and window/capture research, what exact recovery is required after replacing an ad-hoc build: automatic prompt, manual toggle, remove-and-readd, app restart, or logout. Apple documents the identity limitation but not one uniform TCC recovery sequence.
3. Whether moving an unchanged, already-authorized release between `/Applications`, `~/Applications`, and Downloads preserves each required TCC grant. The code signature remains unchanged, but Apple provides no cross-service path guarantee.
4. Whether every changed GitHub download needs a new Gatekeeper **Open Anyway** exception on each supported macOS version, and whether an EdDSA-valid Sparkle replacement changes that result. Gatekeeper's complete invocation and exception-matching policy is intentionally not documented as stable.
5. Whether the selected app architecture can use hardened runtime with all nested code while loading Sparkle. Sparkle explicitly warns about Library Validation with ad-hoc host signing.
6. Whether a full Sparkle regular-bundle update works end to end for an externally downloaded, ad-hoc-signed release on clean systems, including rollback, relaunch, quarantine/Gatekeeper behavior, and post-update TCC recovery.
7. Whether launch at login is needed in the first public version and, if so, whether `SMAppService.mainApp` registration survives an ad-hoc app replacement on every supported OS.
8. Whether any future feature selects a restricted entitlement, App Group, shared keychain group, system extension, or other Team ID-dependent capability. Those features need separate capability-specific evidence and cannot inherit feasibility from ordinary TCC access.

These are release-prototype questions, not reasons to assume favorable behavior. Tests must use artifacts downloaded through the real public channel on clean user accounts or clean systems; running an Xcode build in place does not reproduce quarantine, Gatekeeper, translocation, or public-update identity.

## Recommendation

Proceed with the chosen unsigned public release only under this explicit contract:

1. Produce a complete, consistently **ad-hoc-signed** Apple-silicon app bundle; sign nested code correctly and describe the release as “not Developer ID signed or notarized,” not as literally unsigned.
2. Distribute a simple app archive. Tell users to move it to `/Applications`, attempt one launch, approve it through **System Settings > Privacy & Security > Open Anyway**, and then grant only the required TCC permissions. Do not recommend disabling Gatekeeper or removing quarantine.
3. Keep every first-version feature in the user session. Exclude persistent privileged helpers, LaunchDaemons, package-based updates, restricted entitlements, shared access groups, and any claim that elevation bypasses privacy controls.
4. Treat every changed release as potentially requiring TCC reauthorization. Check required authorization at startup and immediately after update, explain which permission is missing, deep-link to the relevant System Settings pane where supported, and preserve settings outside the app bundle.
5. For the first public version, implement update **notification** rather than unattended replacement. Link users to the GitHub release and explain that replacing the app may require Gatekeeper and privacy approval again.
6. If in-app installation is later adopted, use current Sparkle, HTTPS, EdDSA-signed archives, `SUVerifyUpdateBeforeExtraction`, and a signed feed; keep the private key offline and backed up. Ship only after an external-download update prototype passes on every supported macOS version. Do not present successful EdDSA verification as equivalent to Developer ID or as guaranteeing TCC persistence.
7. Reopen the Developer ID decision if the product requires any of: one-time TCC setup that survives updates, a supported privileged LaunchDaemon, restricted entitlements, managed deployment, dependable keychain/app-group identity, normal Gatekeeper launch, notarization, verified publisher presentation, or genuinely seamless automatic updates.

This boundary supports an experimental, transparent open-source first public version. It does not support a low-friction consumer installation or a release whose core automation is guaranteed to keep working unattended after updates.
